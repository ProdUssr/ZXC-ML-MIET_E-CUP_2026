## 0. Если читать только один абзац

Мы соревнуемся в задаче, где **любая ошибка стоит всего результата**: если наш код упадёт или выдаст хоть одну строку не в том формате — за весь сабмит ноль. Поэтому первым делом мы построили не модель, а **взлётную полосу**: каркас, который физически не умеет падать, всегда успевает к дедлайну и всегда пишет валидный файл. Каркас готов, оттестирован (41 тест зелёный) и прогнан на реальных данных. Внутри него сейчас стоит **временная заглушка вместо модели** — набор regex-правил, дающих **0.61** на нашем holdout против **0.46** у константы. Это ожидаемо слабо. Следующий шаг — вынуть заглушку и вставить туда эмбеддинги, а потом VLM. Каркас спроектирован так, что это **один новый файл и одна строка в конфиге**, без правок остального кода.

## 1. Что просят организаторы

На вход — карточки товаров из двух регулируемых категорий: **БАД** и **Легковоспламеняющиеся** (далее ЛВЖ). У каждой карточки есть название, описание, категория и от 1 до 5 фотографий.

Нужно для каждого товара выдать **две вещи**:

1. **вердикт** — `бан` или `не бан`;
2. **объяснение** для сотрудника-модератора — текст строго 50–300 символов.

Формат строки в выходном CSV:

```
<комментарий>тут текст объяснения<вердикт>бан
```

Закрывающих тегов нет. Колонки на выходе: `id,result`.

**Метрика:** macro-F1 отдельно по каждой категории, потом среднее. То есть маленькая категория весит столько же, сколько большая — нельзя «выехать» на мажоритарном классе.

**Регламент прогона:** три набора подряд — Check (10 товаров, 3 мин) → Public (~1600, 20 мин) → Private (~3800, 40 мин). Лимит времени включает старт контейнера и загрузку весов моделей. Интернета нет. Железо: 20 CPU, 100 ГБ RAM, 1×H100 80 ГБ.

## 2. Пять ограничений, из которых вытекает весь код

Если вы откроете `baseline_1/submission/` и подумаете «зачем тут столько параноидальной обвязки вокруг такой простой модели» — вот ответ. Каждый кусок кода отвечает на конкретную угрозу.

| Ограничение | Что будет, если проигнорировать | Что мы из-за этого сделали |
|---|---|---|
| Падение = 0 очков за **всё** | Один `KeyError` на 3800-й строке — и три недели работы в мусор | Всё тело `main()` под `except BaseException`, выход всегда с кодом 0 |
| Одна невалидная строка = 0 очков | Товар с запятой в описании ломает CSV | Единый модуль формата + санитайзер, вырезающий `< > ; ,` и переводы строк |
| Жёсткий лимит времени | Не успели — файла нет — ноль | Файл с ответами пишется **до** запуска модели, потом только улучшается |
| Категория маленькая (ЛВЖ 198 «хороших» из 5502) | Модель схлопнется в константу | Пороги подбираются отдельно по каждой категории |
| Нет интернета, чужой контейнер | `pip install` не сработает | Каркас — чистый Python stdlib, ноль зависимостей |

Главный принцип, который стоит запомнить: **сначала гарантируем валидный ответ, потом делаем его хорошим.** Не наоборот.

## 3. Что лежит в репозитории

Две ветки — это два **разных** решения, не версии одного.

### `main` → `quality-baseline-submit/`
Бейзлайн организаторов (~250 строк). Схема: Qwen3-VL-Embedding-2B считает эмбеддинги текста+картинок → логистическая регрессия отдельно на каждую категорию → Qwen3.5-4B пишет комментарий → обрезка до 50–300 символов.

Это **эталон качества** и одновременно **пример того, чего мы боимся**: там нет ни одного `try`. Одна битая картинка, один OOM на батче 128 — и сабмит пустой.

### `test_baseline` → `baseline_1/`
Наша разработка. Устроена так:

```
baseline_1/
├── submission/     ← ЭТО и есть сабмит; всё остальное в архив не входит
├── train/          ← обучение калибровки, сплиты, скоринг
├── tests/          ← 41 тест
├── tools/          ← сборка архива, сухой прогон
└── docs/           ← переписка агента с ревьюером (см. раздел 11)
```

Важно: в архив для организаторов уходит **только** папка `submission/` — 26 файлов, 25 КБ. Остальное — наша внутренняя кухня.

## 4. Как устроен `baseline_1`: семь слоёв

Удобнее всего думать об этом как о **заводском цехе**, где на входе конвейер с товарами, а на выходе — заполненный бланк по каждому.

```
                    ┌─────────────────────────────────────┐
   test.csv  ──────▶│  1. ЧТЕНИЕ ВХОДА (io_utils)         │
                    └──────────────┬──────────────────────┘
                                   ▼
                    ┌─────────────────────────────────────┐
                    │  2. ЧЕРНОВИК СРАЗУ НА ДИСК (sink)   │──▶ submit.csv (уже валиден!)
                    └──────────────┬──────────────────────┘
                                   ▼
                    ┌─────────────────────────────────────┐
                    │  3. ХРОНОМЕТРИСТ (deadline)         │  решает, насколько
                    └──────────────┬──────────────────────┘  можно «шиковать»
                                   ▼
                    ┌─────────────────────────────────────┐
                    │  4. ДИСПЕТЧЕР (router/orchestrator) │  режет на батчи,
                    └──────────────┬──────────────────────┘  ведёт каскад стадий
                                   ▼
                    ┌─────────────────────────────────────┐
                    │  5. МОЗГ (rules + calibration)      │  ← СЮДА встанет модель
                    └──────────────┬──────────────────────┘
                                   ▼
                    ┌─────────────────────────────────────┐
                    │  6. РЕДАКТОР (explanations + format)│  пишет комментарий
                    └──────────────┬──────────────────────┘
                                   ▼
                    ┌─────────────────────────────────────┐
                    │  2'. ПЕРЕЗАПИСЬ ЧЕРНОВИКА (sink)    │──▶ submit.csv (улучшен)
                    └─────────────────────────────────────┘

              7. ТЕЛЕМЕТРИЯ — пишет в stderr всё, что происходило
```

### Слой 1. Чтение входа — `io_utils.py`

Задача: **прочитать что угодно и не умереть**. Заголовки нормализуются (`ID`, `Id`, ` id ` → `id`), длинные поля обрезаются до 50 000 символов, лимит размера CSV-поля поднят до 2 ГБ, кодировка читается с `errors="replace"`. Если файл оборвался на середине — сохраняем то, что успели прочитать, и пишем ошибку в лог.

Аргументы командной строки принимаются во всех известных вариантах (`-i`, `--input`, `--test_data_path`, `--data_path`), плюс из переменных окружения, плюс позиционно. Неизвестные флаги игнорируются с предупреждением, а не роняют процесс. Это защита от того, что организаторы вызовут нас чуть иначе, чем мы ожидали.

### Слой 2. Черновик сразу на диск — `sink.py`

**Самая важная идея во всём проекте.** Порядок такой:

1. Ещё до чтения конфига создаётся файл с заголовком `id,result`.
2. Сразу после чтения входа записывается **полный валидный сабмит**, где вердикт каждого товара взят из априора его категории (для БАД — «не бан», для ЛВЖ — «бан», потому что так распределены классы).
3. Только после этого запускается модель, и она **перезаписывает** ответы там, где может.

Что это даёт: в любой момент времени, включая момент `kill -9`, на диске лежит полный файл с правильными id в правильном порядке. Хуже, чем априор, мы уже не сделаем. Таймаут перестаёт быть катастрофой и становится просто потерей качества.

Технически каждый сброс — это запись всего файла во временный + атомарная замена (`os.replace`) + `fsync`. Файл никогда не бывает наполовину записанным. Сбросы идут по таймеру (раз в 5 секунд), а не по батчу — чтобы будущие 500 маленьких VLM-батчей не превратились в 500 перезаписей.

### Слой 3. Хронометрист — `deadline.py`

Следит, успеваем ли мы, и на основании этого выдаёт «бюджет» — разрешение на роскошь.

Пять уровней:

| Уровень | Картинок на товар | Генерация текста моделью | Смысл |
|---|---|---|---|
| **L0** | 3 | да | всё хорошо, работаем в полную силу |
| **L1** | 1 | нет | подтормаживаем |
| **L2** | 0 | нет | только текст |
| **L3** | 0 | нет | режем эскалации |
| **L4** | 0 | нет | аварийный: только априор |

Логика: замеряем скорость на первых товарах, прогнозируем, сколько займут оставшиеся, сравниваем с остатком времени. Если не успеваем — спускаемся на уровень ниже.

Три защиты от дёрганья:
- **прогрев** — первые 5–15% товаров всегда идут на L0, пока статистика не набралась;
- **гистерезис** — чтобы подняться обратно, нужен запас, а не ровное равенство;
- **минимальные интервалы** — вниз не чаще чем раз в `N/50` товаров, вверх — раз в `N/5`.

Лимит времени оценивается формулой `max(180, min(2400, 0.63·N))` — коэффициент подобран так, чтобы точно попадать в опубликованные пороги Check/Public/Private.

### Слой 4. Диспетчер — `router.py` + `orchestrator.py`

Оркестратор режет товары на батчи, гоняет их через роутер, складывает результаты в sink и раз в 5 секунд сбрасывает на диск.

Роутер — это **каскад стадий**, описанный в конфиге. Сейчас там одна стадия:

```json
"stages": [{ "predictor": "rules", "escalate_band": [0.0, 1.0], "min_level": "L4" }]
```

В Фазе 1 будет так:

```json
"stages": [
  { "predictor": "rules",     "escalate_band": [0.3, 0.7], "min_level": "L4" },
  { "predictor": "embedding", "escalate_band": [0.4, 0.6], "min_level": "L2" },
  { "predictor": "vlm",                                     "min_level": "L1" }
]
```

Читается так: сначала все товары идут через `rules`. Те, у кого вероятность попала в «серую зону» 0.3–0.7 (то есть правила не уверены), уходят на `embedding`. Кто остался неуверенным после этого — на `vlm`, но только если хронометрист разрешает (`min_level: L1`).

Предикторы подгружаются **лениво по имени из конфига**. Если модуль не импортировался или веса не нашлись — эта стадия просто отключается, остальные работают. Важная деталь: подмена на `rules` разрешена **только нулевой стадии**, чтобы упавший VLM не притворился правилами молча.

### Слой 5. Мозг — `predictors/rules.py` + `calibration.py`

Здесь самое интересное архитектурное решение проекта, и его стоит понять.

Наивный подход был бы: «нашли слово *зажигалка* → значит горючий → бан». Мы так **не** делаем. Вместо этого правила **не выносят приговор вообще** — они только описывают, какие улики нашлись:

```python
{
  "category":          "Легковоспламеняющиеся",
  "has_positive":      True,      # нашлись маркеры рубрики
  "has_negative":      False,     # маркеров-исключений нет
  "n_positive_bucket": "2+",      # позитивных маркеров два или больше
  "explicit_exclusion": False     # явного «не является X» нет
}
```

Эта пятёрка — **«подпись улик»**. Дальше подпись идёт ключом в таблицу `calibration.json`, где для каждой комбинации записано, чем такие товары **на самом деле оказывались в обучающих данных**:

```json
"[\"Легковоспламеняющиеся\",1,0,\"2+\",0]": {
  "count": 858, "label_0": 775, "label_1": 83, "p_regulated": 0.9023
}
```

По-человечески: «в обучающей выборке было 858 таких товаров, из них 775 забанены → вероятность бана 0.90».

**Почему так лучше.** Знак улики не зашит в код, а выучен из данных. Если завтра выяснится, что слово «свеча» на практике коррелирует не с тем, с чем мы думали, — мы не правим логику, мы переобучаем таблицу. И, что важнее, эта же таблица завтра примет признаки от эмбеддингов и VLM: достаточно добавить новые поля в подпись.

Технически таблица — это дерево решений глубины 4, обученное простым подсчётом с сглаживанием Лапласа (α=1). Ячейки меньше 30 наблюдений откатываются к априору категории — чтобы одна случайная строка не определяла судьбу целого класса.

### Слой 6. Редактор — `explanations/` + `result_format.py`

Комментарий собирается из шаблона (по 3 варианта на каждую пару категория×исход, чтобы текст не был одинаковым во всех строках) плюс вырезка ±25 символов вокруг найденной улики.

`result_format.py` — единственный источник истины по формату. Там лежит регулярка, которой мы сами себя проверяем:

```
^<комментарий>[^<>\n\r]{50,300}<вердикт>(бан|не бан)$
```

Санитайзер вырезает `<`, `>`, `;`, `,` и переводы строк — чтобы поле пережило даже наивный парсер, который делит строку по запятой. `fit_length()` гарантирует коридор 50–300: короткое дополняется, длинное режется по границе слова. Property-тест на 60 000 случайных входов не нашёл ни одного невалидного результата.

### Слой 7. Телеметрия — `telemetry.py`

В конце прогона в stderr падает одна JSON-строка со всей статистикой: сколько товаров прошло через какую стадию, сколько решено априором, распределение вероятностей по корзинам, тайминги по этапам, история переходов по уровням, сколько строк sink отверг как невалидные. Это наш единственный способ понять, что произошло внутри чужого контейнера.

## 5. Путь одного товара насквозь

Возьмём реальный пример из нашего smoke-теста.

**Вход:** `id=unsafe`, категория `Легковоспламеняющиеся`, название «Спички набор», описание «...горючее вещество...»

1. **Чтение.** Создаётся объект `Item(row_index=1, id="unsafe", ...)`. Номер строки запоминается — он гарантирует, что порядок на выходе совпадёт с порядком на входе, даже если модель вернёт ответы вразнобой.
2. **Черновик.** В файл уже записано: `unsafe,<комментарий>...<вердикт>бан` — потому что априор ЛВЖ = 96% банов.
3. **Бюджет.** Хронометрист говорит L0 — времени навалом.
4. **Правила.** Текст нормализуется (нижний регистр, ё→е). Находятся маркеры `спич*` и `горюч*` — два позитивных. Негативных нет. Подпись улик: `("ЛВЖ", 1, 0, "2+", 0)`.
5. **Калибровка.** Ищем эту подпись в таблице → `p_regulated = 0.9023`.
6. **Порог.** Для ЛВЖ порог 0.9279. `0.9023 < 0.9279` → вердикт **«не бан»**.
7. **Комментарий.** Берётся шаблон «allowed» для ЛВЖ, в него подставляется вырезка «спички набор горючее вещест».
8. **Результат:** `<комментарий>В карточке учтена улика спички 'набор' горючее вещест. По совокупности доступных признаков товар не подтверждён как самостоятельный источник огня...<вердикт>не бан`

Прочитали и поморщились? Правильно. Об этом — следующий раздел.

## 6. Что модель выучила на самом деле (и почему объяснения выглядят странно)

Вот вся таблица по ЛВЖ:

| Что нашли в тексте | Товаров | Доля банов | Вердикт при пороге 0.9279 |
|---|---:|---:|---|
| вообще ничего | 414 | 0.928 | **бан** |
| 1 позитивный маркер | 254 | 0.957 | бан |
| **2+ позитивных, без негативных** | 858 | 0.902 | **не бан** |
| 2+ позитивных + негативные | 1963 | 0.989 | бан |

Товар с **наибольшим** числом признаков горючести — единственный, кто получает «не бан». Это не баг в коде, это правда про данные: в категории ЛВЖ 96.4% товаров забанены, и различия между ячейками (0.90 против 0.96) — почти шум.

**Здесь и лежит главная концептуальная путаница проекта.** Переменная называется `p_regulated` — «вероятность, что товар относится к регулируемой рубрике». Но обучена она на метке `label`, то есть фактически это **«вероятность бана»**. Это разные вещи:

- *«товар — зажигалка»* — вопрос о свойствах товара;
- *«карточку надо забанить»* — вопрос о решении модератора.

Шаблоны объяснений написаны в терминах первого, а вердикт приходит из второго. Поэтому мы получаем тексты, которые сами себе противоречат:

| Товар | Вердикт | Что пишет комментарий |
|---|---|---|
| «Спички набор, горючее вещество» | не бан | «товар **не подтверждён** как источник огня» |
| «Протеин» (по рубрике — прямое **исключение** из БАД) | бан | «этот признак **относит** товар к БАД» |
| товар без единого маркера | бан | «При проверке **найден фрагмент** *маркеры рубрики не найдены*» |

Для задачи, где объяснение читает живой модератор, это критично. Чинить надо не текстовку, а развязать две величины: считать отдельно «вероятность принадлежности рубрике» (для объяснения) и «вероятность бана» (для вердикта).

Для сравнения, по БАД правила работают осмысленно: карточка, где явно написано «БАД», в 88% случаев имеет `label=1`. То есть в этой категории «качественная карточка» ≈ «карточка честно себя маркирует», и текстовые правила это ловят.

## 8. Известные проблемы, по приоритету

### P0 — чинить до того, как вставим модель

**8.1. Пороги стоят ровно на значении ячейки.** Порог для БАД = 0.47547974413646055, и это в точности значение одной из ячеек. Сдвиг на `1e-6` переворачивает 936 карточек БАД (15% категории) и 414 ЛВЖ. Метрика от этого не изменится, но устойчивость — принципиально, а когда придут дробные скоры от эмбеддингов, граничные пороги начнут переворачиваться постоянно.
*Фикс:* в `train/fit_calibration.py` возвращать середину интервала между соседними значениями, а не граничную точку. Одна строка. Ожидаемо: БАД ≈ 0.385, ЛВЖ ≈ 0.915.

**8.2. `explicit_exclusion` ловит не то.** Регулярка `\bне\s+содержит\b` срабатывает на «не содержит сахара / глютена / ГМО» — это стандартная нутрициологическая приписка на любой БАД-карточке, а вовсе не исключение из рубрики. То же с «не является лекарственным средством». В результате в ячейку `["БАД",0,1,"0",1]` попали 182 карточки, из которых 152 реально забанены, — а зашитый в код cap `p ≤ 0.01` принудительно объявляет их все «не бан».
**Цена этого: −0.037 macro-F1 по БАД** (0.7119 без капа против 0.6743 с ним).
*Фикс:* требовать после отрицания объект рубрики — «не является БАД / биологически активной добавкой / пищевой добавкой». Убрать голое «не содержит». Переобучить таблицу и, скорее всего, убрать cap совсем.

### P1 — чинить параллельно с моделью

**8.3. Объяснения противоречат вердикту** (раздел 6). Нужно развести «вероятность рубрики» и «вероятность бана» либо переписать шаблоны в нейтральных терминах решения, а не свойств товара.

**8.4. HTML в описаниях.** В корневом README висит TODO про удаление HTML-тегов, и он до сих пор не сделан. В карточках Ozon тегов много, и они ломают окна вырезки улик (±25 символов могут целиком уйти в `<br/><p style=...>`).

**8.5. Ни разу не запускались в контейнере с `--network none`.** Сейчас это не страшно, потому что зависимостей нет. Когда появятся веса моделей, холодный старт станет главным риском стадии Check (3 минуты на всё).

### P2 — косметика

- `has_positive` полностью выводится из `n_positive_bucket` — признак избыточен, раздувает число ячеек.
- `group_kfold_indices` написан и протестирован, но нигде не используется; при 18 ячейках один holdout даёт шумную оценку.
- Паттерн `\bгаз плит\w*\b` (с пробелом внутри «стема») не поймает «газовая плита».
- Маркер `свеч*` поймает «свеча зажигания».
- На уровне L4 оркестратор не вызывает предикторы вообще, хотя правила стоят почти ноль — теряем бесплатный сигнал.

## 9. Куда двигаться

### Шаг 1 (главный по соотношению цена/качество): эмбеддинги

Взять схему бейзлайна организаторов — Qwen3-VL-Embedding-2B + логрег на категорию — и **вставить внутрь нашего каркаса**, а не рядом с ним.

Что конкретно:
1. В `submission/predictors/embedding.py` (файл уже есть, там заглушка) реализовать `load()` и `predict_batch()`. **Все тяжёлые импорты — строго внутри `load()`**, иначе падение импорта torch уронит весь процесс.
2. Расширить подпись калибровки непрерывной компонентой: добавить в неё, например, децильную корзину скора эмбеддинга. Таблица тогда учитывает и правила, и эмбеддинг одновременно.
3. Добавить стадию в `config.json`.

*Критерий приёмки:* среднее macro-F1 на holdout ≥ 0.75; при искусственно сломанной загрузке весов прогон всё равно завершается с полным валидным файлом и `load_error:embedding = 1` в телеметрии.

Заодно проверить кэш эмбеддингов: 3800 товаров × 5 картинок при батче 128 на H100 — по бюджету должно пройти с большим запасом, но замерить надо до того, как это станет сюрпризом на Public.

### Шаг 2: VLM для того, что текст не ловит

Правила и эмбеддинги принципиально не различают то, на чём построена половина рубрики ЛВЖ:

- «содержит горючее вещество» **против** «предназначен для использования с огнём» (мангал, гриль);
- «источник огня встроен» **против** «источник огня — самостоятельный товар»;
- «горючее — это содержимое» **против** «товар без содержимого»;
- «легковоспламеняющийся предмет входит в комплект» **против** «не входит».

Это ровно те случаи, где нужно посмотреть на фотографию. Ставим VLM третьей стадией с узкой полосой эскалации (только серая зона), `min_level: L1` — чтобы при нехватке времени она отключалась первой.

*Критерий приёмки:* ЛВЖ macro-F1 ≥ 0.65; при принудительном L2 прогон деградирует до эмбеддингов без потери валидности.

### Шаг 3: объяснения

Сейчас это шаблоны. Варианты по возрастанию стоимости:

1. **Дёшево:** починить логику (раздел 6) и оставить шаблоны — риск ноль, качество среднее.
2. **Средне:** генерировать комментарий моделью, но пропускать через `validate_model_comment()` — если модель написала что-то противоречащее вердикту или вылезла из 50–300 символов, откатываемся на шаблон. Механизм отката уже написан и работает.
3. **Дорого:** генерация для всех, шаблон только как аварийный вариант. Тут главный риск — время: генерация 3800 комментариев по 30 слов на 4B-модели.

Рекомендую вариант 2: он даёт основную часть выигрыша при нулевом риске обнуления.

### Чего делать НЕ надо

- **Не улучшать regex-правила.** Потолок текстовых правил уже виден, и он низкий. Каждый час туда — это час не в эмбеддинги.
- **Не трогать `sink.py`, `run.py`, `deadline.py`.** Они работают и покрыты тестами. Если новая фича требует их правки — скорее всего, фича спроектирована неправильно.
- **Не отправлять сабмит без сухого прогона.** `sh tools/dry_run.sh` — обязательный gate.

## 12. Словарь

| Термин | Что значит у нас |
|---|---|
| **`p_regulated`** | Число 0–1, выдаваемое предиктором. Формально «вероятность рубрики», фактически «вероятность бана». См. раздел 6 |
| **Подпись улик (signature)** | Пятёрка признаков, по которой ищется ячейка в калибровочной таблице |
| **Калибровка** | Таблица «подпись → вероятность», обученная подсчётом на train |
| **Стадия / предиктор** | Один шаг каскада: `rules`, `embedding`, `vlm` |
| **Эскалация** | Передача неуверенных товаров на следующую, более дорогую стадию |
| **Бюджет / уровень L0–L4** | Разрешение от хронометриста: сколько картинок можно смотреть, можно ли генерировать текст |
| **Sink** | Компонент, отвечающий за запись результата. Всегда пишет файл целиком и атомарно |
| **Group-safe holdout** | Отложенная выборка, где карточки с одинаковым текстом целиком уходят в одну часть — иначе дубли протекают между train и test (их в данных 1778 групп) |
| **Канарейка** | Ручной тест-кейс на конкретном товаре («Ракетка для бадминтона не должна считаться БАД») |
| **Сухой прогон (dry run)** | Обязательная проверка перед сабмитом: три размера входа + краевые случаи |
