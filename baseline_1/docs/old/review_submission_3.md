## Вердикт

**В текущем виде отправлять не стоит — но не из-за надёжности, а из-за двух вещей разной природы.**

1. **Четыре дефекта дают ровно 0 очков на определённых входах** — все четыре воспроизведены, все четыре чинятся правкой в 1–5 строк. Это блокеры отправки.
2. **По собственным цифрам отчёта решение проигрывает двухстрочной константе**: 0.2651 против 0.4584 (category macro mean). Сабмит в таком виде не просто «слабый» — он тратит попытку на результат хуже, чем `верни мажоритарный класс категории`.

Каркас надёжности при этом действительно стал сильнее, чем в v1: атомарный полный снапшот, отсутствие фоновых воркеров, разведённая полярность приоров и правил — всё подтверждено прогонами. Проблема сместилась с «упадёт» на «упадёт на редком входе + предсказывает не то».

# Блокеры отправки (P0)

## P0-1. Описание длиннее 131 072 символов роняет процесс до создания выходного файла

```
_csv.Error: field larger than field limit (131072)
→ exit 1, выходного файла НЕТ
```

Воспроизведено: строка с описанием в 200 000 символов. `csv.field_size_limit` по умолчанию 131 072; `read_items` не устанавливает лимит и не обёрнут в `try`. Отчёт заявляет тест на 100 000 символов — это ниже порога, поэтому дефект и не поймался.

На маркетплейсе описание в 200 КБ — не экзотика (вставленная таблица характеристик, спам-простыня ключевых слов). Одна такая строка в закрытом наборе = обнуление стадии.

## P0-2. Любой лишний аргумент командной строки роняет процесс до создания выходного файла

```
run.py: error: unrecognized arguments: --gpu 0
→ exit 2, выходного файла НЕТ
```

`argparse` с `required=True` и без `parse_known_args`. Вы не контролируете точную строку запуска проверяющей системы: `metadata.json` задаёт `python -u run.py`, аргументы дописывает оркестратор организаторов. Если они добавят хоть один флаг, которого нет в парсере (или переименуют `-i`), решение не создаст файл вообще.

## P0-3. Любая ошибка чтения входа = нет выходного файла (регресс относительно v1)

В v1 выходной файл создавался **до** чтения входа, и ревью v1 это отдельно хвалило. В v2 порядок в `run.py`: `parse_args → load_settings → read_items → ResultSink(...) → sink.flush()`. Всё, что падает до четвёртой строки, оставляет пустую директорию. Воспроизведено на несуществующем входном файле (`FileNotFoundError`, exit 1, файла нет).

Это тот же класс, что P0-1 и P0-2, но общая причина: **нет внешнего `try/except` вокруг всего `main()` и нет гарантированного «хоть какого-то» выхода**.

## P0-4. `sys.path.insert(0, ROOT.parent)` позволяет соседнему файлу перехватить импорт

```python
if str(ROOT.parent) not in sys.path:
    sys.path.insert(0, str(ROOT.parent))
```

Воспроизведено: положил `settings.py` рядом с директорией распаковки → импортировался он, а не модуль сабмита.

Архив распаковывается в директорию, содержимое которой вы не контролируете. В `sys.path[0]` попадает её родитель — вместе со всем, что там лежит, включая потенциальные `csv.py`, `json.py`, `settings.py`. Ветка `from submission.X import ...` в `run.py` вообще не нужна: `run.py` — это корневой entry point, а подмодули уже имеют собственный `try/except` на относительные импорты.

# Дефекты, критичные для Фазы 1 (P1)

## P1-5. Дедлайн-менеджер сваливается в L4 сразу после первого батча, если загрузка модели заметная

Симуляция: 3800 товаров, 120 с на загрузку модели, реальный темп 0.35 с/товар (уложились бы в 1464 с при бюджете 2040 с).

```
done=    0  elapsed= 120.0  level=L0
done=  256  elapsed= 209.6  level=L4   ← полная деградация
done=  512  elapsed= 299.2  level=L4
done= 1024  elapsed= 478.4  level=L1
done= 2048  elapsed= 836.8  level=L0
```

Причина в `deadline.py`:

```python
ratio = (elapsed / max(1, self.done) * (self.n_items - self.done)) / max(remaining, 1e-6)
```

`elapsed` считается от `_T0` и включает загрузку модели, поэтому темп на первом батче оценивается как (120+89.6)/256 = 0.82 с/товар вместо реальных 0.35. Прогноз 2903 с при остатке 1830 → ratio 1.59 → L4.

Дальше система «самоисправляется» (в L4 она быстрая, оценка темпа падает), но **первые ~700 товаров уже обработаны голым приором категории**. В Фазе 0 это невидимо (init 0.07 с), в Фазе 1 это гарантированная потеря качества на старте каждого прогона.

Нужно: считать темп от момента старта обработки, а не от `_T0`; init учитывать как вычет из бюджета, а не как часть per-item стоимости. И не переключать уровень по оценке, построенной на одном батче — нужен прогрев (например, минимум 3 батча или 5% товаров).

## P1-6. `hard_limit_for` — ступенька, ошибка в размере набора = таймаут

```python
if n <= 10:   return 180.0
if n <= 2000: return 1200.0
return 2400.0
```

Public ~1600 → 1200 с ✓. Но набор в 2500 товаров получит бюджет 2400 с при реальном лимите 1200 с → уверенный таймаут → 0. И наоборот, Check из 20 товаров получит 1200 с при реальных 180. Точные размеры закрытых наборов вам никто не гарантировал — архитектурный документ не зря предлагал непрерывную формулу `max(180, 0.6·N)`. Ступенька с обрывом ровно там, где стоит ваша оценка размера Public, — это ставка, а не оценка.

## P1-7. Один упавший предиктор роняет весь каскад

Воспроизведено: второй стадией добавлен предиктор, бросающий исключение в `load()`. Результат — `router.load()` пробрасывает наружу, `orchestrator.run()` не вызывается вообще, все 10 строк получают чистый приор категории. **Успешно загруженная стадия `rules` не отрабатывает.**

Для Фазы 1 это главный архитектурный риск: VLM не влезла в память / несовместимая версия vLLM / нет весов → вы теряете не VLM-стадию, а *весь каскад*, включая работающие правила. Деградация должна быть постадийной: стадия, которая не загрузилась, выбывает из списка с записью в телеметрию, остальные работают.

То же и в `predict_batch`: там исключение уже ловится постадийно (`router.run`), но `load` — нет. Асимметрия.

## P1-8. Стоимость `flush` растёт как O(N²/batch), а `flush_interval_sec` — мёртвый ключ

`Orchestrator.run` вызывает `self.sink.flush()` после **каждого** батча, безусловно. Ключ `flush_interval_sec: 5.0` парсится в `Settings`, но нигде не читается — `grep` подтверждает. При этом ADR 001 обосновывает стоимость полного перезаписывания именно «пятисекундной каденцией», которой не существует.

Замеры на N=4000:

| batch_size | flushes | суммарно на flush | wall |
|---:|---:|---:|---:|
| 256 | 18 | 0.68 с | 1.11 с |
| 32 | 127 | 5.5 с | 5.95 с |
| 8 | 502 | **21.9 с** | 22.4 с |

`batch_size=8` — совершенно реалистичный размер батча для VLM. 22 секунды чистого I/O (полная перезапись + `fsync` + `os.replace` на каждый батч) на локальном SSD; на диске проверяющей системы это может быть кратно больше. Плюс это время попадает в `elapsed` и через P1-5 подталкивает к деградации.

Идея ADR 001 правильная — цена реализации нет. Нужно развязать «частоту предсказаний» и «частоту снапшотов»: `flush()` по таймеру (`flush_interval_sec`) плюс обязательный flush в `finalize`.

## P1-9. Манифест изображений: глобальный проход, устаревший бюджет, недетерминированный выбор

Три отдельные проблемы в одном шве:

- **Недетерминированность.** `image_root.joinpath(item.id).iterdir()` без сортировки. Проверено: из `a.jpg, b.png, c.jpg, m.webp, z.jpeg` при `max_images=3` выбрались `z.jpeg, a.jpg, c.jpg`. Какие три из пяти изображений попадут в модель — зависит от порядка записей в директории. A/B-эксперименты Фазы 1 на этом становятся невоспроизводимыми, а «первое изображение товара» получить нельзя в принципе.
- **Единый снапшот бюджета.** `attach_images(working, root, self.deadline.budget())` вызывается один раз до цикла батчей. Если дедлайн-менеджер позже уронит уровень с L0 до L1 (`max_images` 3→1), это ни на что не повлияет — изображения уже прикреплены по старому бюджету. Деградация по изображениям, ради которой таблица L0–L4 и заведена, не работает.
- **Форма шва.** Полный проход по всем товарам до начала обработки. В Фазе 0 это `iterdir` и стоит миллисекунды; в Фазе 1 сюда добавится декодирование и ресайз — и первое предсказание не начнётся, пока не обработаны все 3800 товаров. Архитектурный документ требует потоковый prefetch с ограниченной очередью; текущий шов имеет форму «сначала всё, потом всё».

## P1-10. Нет проверки заголовков входного CSV

Проверено: файл с колонкой `ID` вместо `id` → все `id` пустые, ни одного предупреждения, exit 0, «валидный» файл с нулевым скором. Это ровно тот же класс отказа, что BOM-баг v1, — его починили точечно (`utf-8-sig`), но не закрыли класс. Достаточно после чтения проверить, что колонки `id`/`name`/`description`/`category` найдены, а доля непустых `id` близка к 1, и громко орать в stderr иначе.

## P1-11. Правила: сигнатура улик направлена против данных

Это главная причина цифры 0.2651.

Отчёт честно приводит конфликт, но интерпретирует его как **нерешённый вопрос о `label_mapping`**. Это, похоже, неверная рамка. Маппинг как раз закрыт: в бейзлайне организаторов `verdict_map = {1: "не бан", 0: "бан"}` — цитата в отчёте есть, и она авторитетна. Открыт другой вопрос — **что именно делает карточку плохой**.

Цифры отчёта читаются однозначно:

| категория | маркер есть | маркер есть, label=1 | маркер отсутствует, label=1 |
|---|---:|---:|---:|
| БАД | 6739 | 5439 (80.7%) | 125 / 730 (17.1%) |
| ЛВЖ | 4092 | 169 (4.1%) | 29 / 1410 (2.1%) |

Для БАД **наличие маркировки коррелирует с label=1, то есть с «не бан»**. Это согласуется с содержательной трактовкой рубрики: банится не «товар является БАД», а «товар является БАД и не имеет обязательной маркировки/дисклеймера». Правила же жёстко зашивают `наличие маркера БАД → p_regulated = 0.78 → бан`, то есть предсказывают ровно наоборот. Отсюда 0.2651.

Проверил, что даст простая замена знака (посчитано по полным цифрам отчёта, не по holdout — оценка сверху):

| стратегия | БАД macro-F1 | ЛВЖ macro-F1 | category macro mean |
|---|---:|---:|---:|
| текущая (shipped, `direct`) | 0.2931 | 0.2372 | **0.2651** |
| константа-мажоритарий | 0.4269 | 0.4908 | **0.4589** |
| улика → label=1 (знак по данным) | **0.6717** | 0.4908 | **≈0.581** |

(Моя реконструкция константного бейзлайна даёт 0.4589 против 0.4584 в отчёте — модель ситуации сходится.)

То есть: DoD-гейт «побить мажоритария в обеих категориях раздельно» **достижим на БАД прямо сейчас**, без единой новой модели. По ЛВЖ маркеры почти не разделяют (4.1% против 2.1%) — там честно ничья с константой, и это нормально для Фазы 0.

Ключевой вывод не «поменяйте знак», а **архитектурный**: знак связи улики с вердиктом не должен быть литералом в коде. Правила обязаны отдавать *улики*, а отображение «сигнатура улик → p_regulated» должно быть подобранной по train таблицей, лежащей рядом в JSON. Это и чинит текущий баг, и создаёт тот самый шов, куда в Фазе 1 встанут скоры эмбеддингов и VLM.

Отдельно, мелочи в словарях (проверено прогоном):

| вход | выдаётся | комментарий |
|---|---|---|
| «Лакомство для собак» (ЛВЖ) | бан | `\bлак\w*\b` ловит «лакомство» |
| «Зажигалка со встроенным фонариком» | не бан | `встроенн` в негативе имеет абсолютный приоритет и гасит «зажигалк» |
| «Пауэрбанк, встроенный аккумулятор» | не бан | то же |
| «Краска для волос» | бан | `краск` — слишком широкий стем |

Абсолютный приоритет негативного списка над позитивным означает, что одна широкая негативная основа перечёркивает произвольное число позитивных улик. Это не тюнинг словаря, а свойство схемы разрешения конфликтов.

# Оценка масштабируемости и модифицируемости

## Что сделано правильно и стоит сохранить

- **`contracts.py` без единого внутреннего импорта.** Настоящий контрактный слой; `Item`/`Prediction`/`Budget`/`Predictor` покрывают Фазу 1 без изменения сигнатур. Это лучшая часть проекта.
- **Реестр предикторов с ленивым импортом (ADR 003).** Проверил: добавление предиктора действительно требует одного файла и одной строки конфига, `run.py`/`router.py`/`orchestrator.py`/`sink.py` не трогаются. Заявка README подтверждается.
- **Каскад как данные.** `stages`, `escalate_band`, `min_level` в JSON — переключение между Вариантами 1/2/3 архитектурного документа действительно конфиг, а не переписывание.
- **Атомарный снапшот, независимый от порядка.** Единственно верное решение под continuous batching.
- **Изоляция точек правды.** `label_semantics.py` и `result_format.py` — единственные владельцы своих литералов; `p_regulated_from_p_label1` вызывается ровно на границе приоров. Дисциплина выдержана.

## Где архитектура не выдержит Фазу 1

| # | Шов | Проблема | Что сломается |
|---|---|---|---|
| 1 | `Budget` как frozen-снапшот на батч | Предиктор «никогда не смотрит на часы» подан в отчёте как достоинство, но это значит, что **длинный батч нельзя прервать**. Батч из 256 товаров в VLM — это минуты | Дедлайн-менеджер узнает о перерасходе только после того, как перерасход случился |
| 2 | `attach_images` | Глобальный проход + устаревший бюджет + недетерминированный порядок (P1-9) | Prefetch не реализуем без переписывания шва; деградация по изображениям не работает |
| 3 | Отсутствие конкурентности где-либо | Правильная реакция на P0-1 из v1 («убрали воркеры»), но CPU-препроцессинг из раздела A.2 архдокумента (16 воркеров, иначе ~570 с на декодирование) втыкать некуда | Полбюджета Private уходит на однопоточный декод JPEG |

Мелочи того же ряда: `predictors.discover()` не вызывается нигде; `Router._build` сначала смотрит в `REGISTRY`, который на момент вызова пуст (декораторы ещё не отработали), поэтому инъекция реестра фактически не работает и всегда идёт путь `build()`; `ImageLoader` — пустая заглушка без сигнатуры, которую кто-либо вызывает.

# Инструкция для агента

Задача — довести сабмит до состояния «не обнуляется ни на каком входе» и «архитектура держит Фазу 1». Идейных улучшений не добавлять. Порядок — по убыванию цены ошибки.

## Блок A. Устранить обнуления (обязательно до любой отправки)

**A1. Сделать создание выходного файла первым, что делает процесс.**
Перестроить `main()` так, чтобы порядок был: `parse_args (устойчивый) → создать выходной файл с заголовком → read_items → sink → всё остальное`. Обернуть **всё тело `main()`** в `try/except BaseException`, в обработчике — записать хоть что-то валидное и вернуть 0. Ни один путь исполнения не должен завершаться без существующего выходного файла.
*Критерий приёмки:* прогон с несуществующим входным файлом, с битым CSV и с пустым файлом даёт exit 0 и существующий выходной файл.

**A2. Снять лимит поля CSV и защитить чтение.**
В `io_utils.read_items`: `csv.field_size_limit(min(sys.maxsize, 2**31 - 1))` до открытия файла; обрезать `name`/`description` до разумного потолка (например, 50 000 символов) прямо при чтении; чтение обернуть в `try/except (OSError, csv.Error, UnicodeError)` с возвратом того, что успели прочитать, и записью в stderr.
*Критерий приёмки:* CSV со строкой в 500 000 символов обрабатывается, exit 0, все id на месте.

**A3. Сделать разбор аргументов неубиваемым.**
Заменить `parse_args` на `parse_known_args`, убрать `required=True`, добавить синонимы (`-i/--input/--test_data_path/--data_path/--test-data-path`, `-o/--output/--output-path/--output_path`), при отсутствии значения — позиционный фолбэк и разумные умолчания (`./test.csv`, `./submission.csv` или пути из окружения). Неизвестные аргументы — в stderr, не в `SystemExit`.
*Критерий приёмки:* `run.py -i X -o Y --gpu 0 --whatever` отрабатывает с exit 0.

**A4. Убрать перехватываемость импорта.**
В `run.py` удалить ветку `from submission.X import ...` целиком и удалить `sys.path.insert(0, str(ROOT.parent))`. Оставить только `sys.path.insert(0, str(ROOT))` и плоские импорты. Подмодули уже имеют собственный `try/except` — их не трогать. Если пакетный импорт нужен `train/offline_predict.py`, пусть путь добавляет сама тренировочная обвязка.
*Критерий приёмки:* файл `settings.py`, положенный в родительскую директорию распаковки, не влияет на прогон.

**A5. Проверять заголовки входа.**
После `read_items` — убедиться, что найдены колонки `id`, `name`, `description`, `category` (сравнение по `strip().lower()`), и что доля непустых `id` > 0.99. Иначе — попытаться нормализовать имена колонок по регистру/пробелам, а если не вышло — `LOG.error` с перечислением фактических заголовков. Это должно быть громко видно в stderr прогона.
*Критерий приёмки:* CSV с колонкой `ID` обрабатывается корректно; CSV без колонки id даёт явную ошибку в логе, а не тихий нулевой скор.

## Блок B. Починить полярность и открыть шов калибровки

**B1. Развести две вещи в отчёте и в коде: маппинг label↔вердикт и знак связи улики с вердиктом.**
Маппинг закрыт: `verdict_map = {1: "не бан", 0: "бан"}` из бейзлайна организаторов — оставить `label_mapping: direct` и убрать его из списка блокеров. Открытый вопрос переформулировать как «какая функция от улик предсказывает label», и решать его данными, а не флагом.

**B2. Правила должны отдавать признаки, а не готовую вероятность.**
Изменить `RulesPredictor._predict_one` так, чтобы он вычислял **сигнатуру улик** — например кортеж `(category, has_positive, has_negative, n_positive_bucket)` — и складывал её в `Prediction.evidence` (или в новое поле `features: dict`, если удобнее; контракт `Prediction` дополнить, не ломая существующие поля). Финальную вероятность правила больше не назначают.

**B3. Ввести калибровочную таблицу как данные.**
Добавить в архив `calibration.json`: отображение `сигнатура → p_regulated`, посчитанное офлайн на train как `1 − доля label=1` в ячейке (с сглаживанием Лапласа и минимальным размером ячейки, скажем 30, иначе откат к приору категории). Загружать в `BasePredictor.load()`. Все стадии получают одну и ту же функцию `signature → p_regulated`. Скрипт подгонки таблицы положить в `train/`, в архив не класть.
*Критерий приёмки:* на group-safe holdout category macro mean ≥ 0.55 и по БАД строго выше константного мажоритария; воспроизводится запуском скрипта подгонки.
*Ориентир из моего расчёта по полным данным:* БАД ≈ 0.67, ЛВЖ ≈ 0.49 (ничья с константой — это ожидаемо и приемлемо), среднее ≈ 0.58.

**B4. Убрать абсолютный приоритет негативного списка.**
Негативная улика не должна обнулять произвольное число позитивных. Заменить на композицию сигнатуры (`has_positive`, `has_negative` — два независимых бита, а не приоритет), а исход брать из таблицы B3. Заодно сузить слишком широкие основы: `лак` → `лак`, `лака`, `лаком`, `лакокрасоч` явным списком вместо `\bлак\w*\b`; `краск` — аналогично; `встроенн` из абсолютного вето перевести в обычный признак.
*Критерий приёмки:* «Лакомство для собак» и «Зажигалка со встроенным фонариком» дают ожидаемые вердикты; пять канареек из ревью v1 (`бадминтона`, `бадяга`, «не является БАД», `негорючий`, «не воспламеняется») остаются зелёными.

## Блок C. Архитектура под Фазу 1

**C1. Постадийная деградация при загрузке.**
В `Router.load` обернуть `predictor.load(ctx)` в `try/except`: при исключении — `LOG.exception`, счётчик `load_error:<name>` в телеметрию, стадия исключается из `self.predictors`, цикл продолжается. Если не загрузилась ни одна стадия — работать на приорах, но `orchestrator.run` всё равно вызвать.
*Критерий приёмки:* каскад `[rules, падающий_предиктор]` даёт те же предсказания, что и одиночный `rules`, а не приоры.

**C2. Отвязать flush от батча.**
В `Orchestrator.run` вызывать `sink.flush()` только если `time.monotonic() - last_flush >= settings.flush_interval_sec`, плюс безусловный flush в `finalize()`. Ключ `flush_interval_sec` перестаёт быть мёртвым. ADR 001 дополнить: обоснование стоимости опирается на каденцию — теперь она действительно есть.
*Критерий приёмки:* N=4000 при `batch_size=8` — суммарное время flush < 2 с (сейчас 21.9 с), число flush'ей соответствует длительности прогона, а не числу батчей.

**C3. Исправить оценку темпа в дедлайн-менеджере.**
Ввести `t_processing_start`, фиксируемый после `router.load()`. Темп считать как `(now − t_processing_start) / done`. Время инициализации вычитать из бюджета один раз, а не размазывать по товарам. Добавить прогрев: пока `done < max(3 батча, 0.05·N)` — держать L0 (кроме срабатывания `reserve_sec`). Добавить гистерезис: возврат на уровень вверх только если прогноз ниже порога уровня с запасом (например, на 0.05), чтобы не дребезжало.
*Критерий приёмки:* на симуляции «init 120 с + 0.35 с/товар, N=3800» уровень остаётся L0 на всём прогоне; на симуляции «init 120 с + 0.8 с/товар» деградация наступает плавно и прогон укладывается в бюджет.

**C4. Заменить ступенчатый `hard_limit_for` на непрерывную оценку.**
`limit = 180.0 if n <= 12 else max(600.0, min(2400.0, 0.63 * n))`, либо любая формула без обрыва рядом с ожидаемым размером Public. Прокомментировать в коде, откуда числа. Дополнительно: если переменная окружения с лимитом присутствует — брать её.
*Критерий приёмки:* нет размера набора, при котором маленькое изменение N меняет бюджет более чем в полтора раза.

**C5. Перестроить шов изображений на потоковый и детерминированный.**
Три правки: (а) `sorted(...)` при перечислении файлов в `attach_images` — выбор изображений обязан быть воспроизводим; (б) прикреплять изображения **побатчево, внутри цикла**, с бюджетом, полученным на этот батч, а не один раз для всего набора; (в) зафиксировать сигнатуру `ImageLoader.iter_batches(items, budget) -> Iterator[list[LoadedItem]]` и сделать так, чтобы `Orchestrator` вызывал именно её (в Фазе 0 — синхронная реализация без декодирования). Prefetch-пул в Фазе 1 тогда встанет внутрь `ImageLoader`, не трогая оркестратор.
*Критерий приёмки:* повторный прогон на одном входе даёт побайтово идентичный список `image_paths`; понижение уровня с L0 до L1 в середине прогона реально уменьшает число прикрепляемых изображений.

**C6. Дать предикторам возможность прерваться.**
Добавить в `Budget` поле `deadline_monotonic: float` (абсолютный момент, к которому батч обязан завершиться) — это не заставляет предиктор «читать часы», но даёт ему остановиться. `RulesPredictor` его игнорирует; VLM-предиктор Фазы 1 будет проверять его между микробатчами и возвращать частичный результат. Оркестратор дополняет недостающие строки дефолтами — механизм уже есть в `_consume`.
*Критерий приёмки:* контракт зафиксирован и покрыт тестом; предиктор, возвращающий предсказания для половины батча, не ломает полноту выхода.

**C7. Расширить телеметрию до отлаживаемой.**
Добавить: счётчик отклонений в `ResultSink.submit` (когда `is_valid_result` вернул False — сейчас предсказание молча превращается в дефолт), гистограмму `p_regulated` по 10 корзинам, число товаров по стадиям и уровням деградации, `init` отдельно от `predict`, число прикреплённых изображений. Оставить формат одной JSON-строки под `run_summary`.
*Критерий приёмки:* по одной строке stderr можно ответить, сколько товаров решено правилами, сколько приором, сколько отброшено валидатором и на каких уровнях шла обработка.
