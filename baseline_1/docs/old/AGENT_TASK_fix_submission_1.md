## 1. Баги, которые нужно исправить (с репродукцией и критерием приёмки)

### Баг №1 — Порог `threshold_flammable` совпадает со счётом «нет маркера» → массовый ложный «бан»

**Репродукция:**
```python
import sys; sys.path.insert(0, "submission")
import rules, label_semantics as ls
item = {"category": "Легковоспламеняющиеся", "name": "", "description": "Симпатичный чехол для телефона с ярким принтом"}
score, fired = rules.predict(item, {"Легковоспламеняющиеся": 0.036})
print(score, fired)                      # 0.15 ['none:no_direct_marker']
print(ls.verdict_from_score(score, 0.15))  # 'бан'  <-- любой товар без маркера в этой категории банится
```
Причина: `rules.py` жёстко возвращает `0.15` для «нет прямого маркера», `config.yaml` даёт `threshold_flammable: 0.15`, сравнение `score >= threshold` — инклюзивное. Категория «БАД» этой коллизии не имеет (`0.15 < 0.50`).

**Что нужно сделать:**
1. Не «отодвинуть число руками». Порог обязан быть получен методом из Шага 4 исходного ТЗ: перебор на train по macro-F1 (обеим трактовкам из В2), раздельно по категориям. Если реального `data.csv` в твоей среде нет — явно зафиксируй это в отчёте как допущение и выбери порог **строго между** соседними дискретными бакетами скора (`rules.py` возвращает всего 5 возможных значений: `prior_bad|prior_flammable`, `0.05`, `0.15`, `0.65..0.95`, плюс дефолт неизвестной категории `0.5`) — так, чтобы граница не совпадала ни с одним из них буквально.
2. Score-функция в `rules.py` устроена как набор из 4–5 фиксированных констант — это и есть корень проблемы (любой порог рано или поздно на что-то из них ляжет один в один). Замени точечные константы на диапазоны/формулу с большей гранулярностью **или** явно задокументируй в коде рядом с каждой константой, с каким порогом она не должна совпадать, и добавь юнит-тест-канарейку, который проверяет это на уровне кода (см. §5.2), а не только на бумаге.
3. После правки обязательно прогони то же самое: обычный товар без маркеров в категории «Легковоспламеняющиеся» с непустым описанием должен получать «не бан» (если реальные данные не докажут обратное).

**Критерий приёмки:** для всех 5 дискретных значений score из `rules.py` (и для дефолта неизвестной категории) явно посчитан и записан в отчёт вердикт по каждой категории; ни один порог не равен буквально ни одной из констант; тест из репродукции выше даёт `не бан`.

### Баг №3 — Внутренние теги правил утекают в комментарий для человека

**Репродукция:**
```python
import explanations as ex
print(ex.build("БАД", "не бан", ["none:no_direct_marker"]))
# "...выявлено исключающее условие none:no_direct_marker, поэтому товар не отнесён..."
```
Два дефекта сразу: (1) сырой внутренний тег `none:no_direct_marker` виден в тексте для жюри; (2) смысловое противоречие — тег означает «маркеров вообще не найдено», а фраза утверждает, что «выявлено исключающее условие» (то есть неверно даже по смыслу, не только по стилю).

**Что нужно сделать:**
1. В `run.py` при вызове `build_explanation(...)` передавай **человекочитаемую улику**, а не сырой тег: либо вырезанную подстроку из `name`+`description`, которая реально совпала с паттерном (нужно доработать `rules.predict`, чтобы он возвращал не только тег `"positive:бад"`, но и точную позицию/подстроку совпадения), либо заранее прописанную для каждого паттерна короткую человекочитаемую фразу (словарь `паттерн → фраза`), но не сам паттерн как код.
2. Для случая `none:no_direct_marker` (маркеров не найдено вовсе, это не «исключающее условие», а «отсутствие подтверждения») нужен **отдельный** шаблон без слова «исключающее условие» — не переиспользуй шаблон, рассчитанный на реальное срабатывание negative-правила.
3. Добавь автопроверку согласованности вердикт↔комментарий из Шага 5 исходного ТЗ (словарь полярных маркеров × вердикт), которой сейчас нет как отдельного явного слоя — сейчас есть только один частный `if not is_ban and any(r.startswith("positive:") ...)`, это не покрывает все возможные несогласованные комбинации.
4. Доведи число шаблонов минимум до 3–5 **на каждую комбинацию категория × вердикт** (сейчас 2 шаблона на вердикт, категория не учитывается вовсе — только подставляется как слово).

**Критерий приёмки:** прогон генератора по всем возможным `(category, verdict, fired_rule)` из `rules.RULES` не содержит в тексте комментария символов `:` рядом с идентификаторами вида `positive:`/`negative:`/`none:` (grep-проверка), и ни один шаблон при `none:no_direct_marker` не утверждает про «исключающее условие».

### Баг №4 — Нет инкрементальной записи CSV: единственная точка отказа при жёстком килле процесса

**Репродукция:** весь вывод формируется в памяти (`results.append`) и пишется на диск один раз, в самом конце `main()`, внутри `finally`. Убедиться:
```bash
grep -n "open(args.output_path" submission/run.py   # ровно одно место — в самом конце
```
Это защищает от Python-исключений (проверено), но НЕ защищает от `SIGKILL`/OOM-killer/внешнего убийства контейнера раньше, чем сработает внутренний `DeadlineManager` — тогда файла не будет вообще. Дополнительно `build_manifest(...)` вызывается **до** создания `DeadlineManager` и не имеет собственного тайм-аута.

**Что нужно сделать — конкретная схема, не изобретать заново:**
1. Открой выходной файл **в начале** `main()` (сразу после парсинга аргументов, до чтения `test.csv`), запиши заголовок `id,result`, держи файловый дескриптор открытым на протяжении всего прогона.
2. В `process()` пиши строки **батчами** (256 штук, как требует исходное ТЗ), а не копи всё в `results`-списке до конца: после каждого батча — `writer.writerows(batch)`, `file.flush()`, `os.fsync(file.fileno())`.
3. Веди счётчик `written_count` (сколько строк реально ушло на диск) как отдельную переменную/атрибут, а не как побочный эффект длины списка в памяти — он должен обновляться **после** успешного `fsync`, не раньше.
4. Финализатор (`pipeline/finalizer.py`) должен измениться: он не должен переписывать уже сброшенные на диск строки заново (иначе дубли id в выводе). При падении/дедлайне он дописывает (`append`-режим или продолжение того же открытого дескриптора) дефолты **только** для товаров с индексом `>= written_count`, и только их.
5. Оберни `build_manifest(...)` собственным тайм-аутом (например, через `concurrent.futures` с `future.result(timeout=...)`, а не голый вызов) — он не должен иметь возможность зависнуть без ограничения по времени до того, как файл вообще открыт на запись.
6. Не сломай при этом гарантию порядка строк = порядку входного файла (И1) и обработку дублей id (документированное поведение — оба дубля должны быть записаны, каждый под своим порядковым номером обработки, а не схлопнуты по `written_count`, который отслеживает **позиции**, а не уникальные id).

**Критерий приёмки:** тест «жёсткого килла» (см. §6.4) — запусти `run.py` в фоне на N=2000, дай проработать половину времени бюджета, пошли `SIGKILL` (не `SIGTERM` — Python не должен успеть перехватить), проверь, что выходной файл существует, содержит заголовок и **строго меньше N**, но **не ноль** валидных строк, соответствующих первым обработанным id по порядку.

## 4. Специфичные ловушки — читай перед тем, как начать чинить

Это не общие пожелания, а конкретные способы, которыми легко ухудшить код при исправлении именно этих багов:

1. **Не патчи `threshold_flammable` на глаз.** Простая замена `0.15` на, скажем, `0.2` без реального прогона по train-данным — это тот же самый баг класса «число из головы», только сдвинутое. Если данных нет — минимум явно перечисли все 5 дискретных значений score и вердикт для каждого, зафиксируй как допущение, а не как решённый вопрос.
2. **Не разводи логику направления label_mapping в двух местах.** Если выбираешь вариант (b) из Бага №2 (флаг реально нужен), не создавай вторую копию словарей `positive`/`negative` вручную скопипащенную — держи один источник (например, JSON/YAML с двумя профилями полярности), иначе нарушишь И7 в новом виде.
3. **При вводе человекочитаемой улики (Баг №3) не тяни в `submission/` тяжёлые NLP-библиотеки** (spacy, pymorphy и т.п.) — это увеличивает размер образа/архива и время холодного старта без пользы для Фазы 0; извлечение подстроки — это `re.search` по уже используемым паттернам, не более.
4. **При добавлении шаблонов (3–5 на категорию×вердикт) не забудь пересчитать длины.** Каждый новый шаблон должен укладываться в целевой коридор 120–220 символов **до** подстановки слотов — проверь программно (скрипт, который печатает `len()` каждого шаблона с максимально длинными реалистичными слотами), не на глаз.
5. **Инкрементальная запись (Баг №4) — самое рискованное место для регресса.** Конкретные ошибки, которых стоит избежать:
   - Не пиши строки повторно при финализации, если они уже сброшены на диск (дубли `id` в выводе — это провал И1 не хуже пропуска).
   - Не переставляй порядок строк — батчинг не должен сортировать/группировать товары, только резать поток на куски фиксированного размера в порядке чтения.
   - Дубли `id` во входном файле — это два **разных** элемента списка `items` (два разных индекса), а не один ключ; `written_count` считает **позиции**, не уникальные id, иначе одна из дублирующихся строк потеряется.
   - `os.fsync` может быть дорогим на каждый батч при малом размере батча — не уменьшай батч ниже 256 без причины, это может съесть бюджет времени на Private (3800 товаров → 15 fsync-вызовов при батче 256, это нормально; при батче 10 — 380 вызовов, уже риск).
   - При использовании `csv.writer` в режиме "дозаписи" следи, чтобы заголовок не продублировался при повторном открытии файла.
   - Тайм-аут на `build_manifest` через `ThreadPoolExecutor`/`concurrent.futures` не убивает реально зависший поток ОС (Python threads нельзя force-kill) — он только перестаёт ждать его результат. Убедись, что зависший скан картинок не блокирует последующую запись файла результата (открытие/запись CSV не должны зависеть от завершения manifest-потока).
6. **Не добавляй сетевые вызовы в `submission/` ради тестирования** (например, случайно оставленный `requests.get` для отладки/скачивания тестовых картинок) — даже временный вызов, забытый в финальном коде, нарушает И6 и обнуляет решение при реальной проверке без интернета.
7. **Не полагайся на `pandas`/сторонние YAML-парсеры**, если их нет гарантированно в образе `odsai/ecup26-quality-baseline:1.0` — весь текущий код нарочно на stdlib (`csv`, кастомный плоский парсер конфига). Если действительно нужна библиотека — сначала проверь, что она есть в образе, и зафиксируй это в отчёте, а не предполагай.
8. **`_PROCESS_STARTED_AT = time.monotonic()`** должен остаться первой исполняемой строкой файла, до всех не-stdlib импортов — это уже сделано верно, не переставляй её при рефакторинге `run.py` под инкрементальную запись.
9. **После каждого патча — не только «код запускается», а весь набор тестов из §6 заново**, включая уже проходившие ранее (регресс-проверка), а не только тест для конкретно исправляемого бага. Баг №4 (переписывание `run.py`/`process()`) — самый вероятный источник тихого регресса по И3 (фолбэк на товар) и И1 (порядок/полнота), потому что меняет структуру главного цикла, которая раньше эти инварианты обеспечивала.
10. **Metric grid search для Бага №1, если данные есть:** не оптимизируй порог по одной трактовке метрики — исходное ТЗ требует держать обе (min(а,б)) как оптимизируемую величину; порог, хороший для одной трактовки и плохой для другой, — типичная ловушка, если проверять только одну версию скорера.
